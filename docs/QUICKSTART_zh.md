# 快速上手

这份指南带你用 trio 完成第一个方案。它不要求编程基础，没有编程专业背景的领域专家也能一步步照做。开发者、设计师、独立开发者和小团队，可以略过自己已经熟悉的部分。

全程由你决定做什么、做得对不对。你希望交出去的角色由 agent 来承担，两个 agent 互相把关。

**开始之前**：trio 适合两种情况：你有某个领域的专业知识，或者你有一个还没成型的想法。它的前提是关键环节始终由你把关：

- 确认方案和原型；
- 回答每个停点的决定；
- 走查；
- 授权合并。

如果你想“一句话做出整个应用”、不想参与这些环节，trio 不是合适的工具。

[English](QUICKSTART.md)

## 你做什么，你永远不用做什么

| 你做的事 | 你永远不用做的事 |
| --- | --- |
| 用自己的话说清想要什么，最好附上例子，或你喜欢的工具的截图 | 读代码、写代码 |
| 每个停点回答几个决定；每个都有默认值，不回答也可以 | 写测试、修测试 |
| 让你看页面时去看，说出哪里不对劲 | 解决代码冲突、管理分支 |
| 说出允许不可逆操作的那句话，比如“合并并推送” | 记住流程：trio 会告诉 agent 该做什么 |
| 不让真实的客户数据进入 agent 的测试 | |

每个停点大约占用你 10 到 30 分钟，每次走查一到两个小时。

## 需要准备什么

1. **两个 agent 会话**：
   - 一个当**审查者**，负责拟方案和检查；
   - 一个当**执行者**，负责写代码。

   可以是两个不同的工具（比如 Claude Code 和 Codex），也可以是同一个工具开两个独立的会话。两家不同的厂商互相检查，效果最好。
2. **两个工具里都装好 trio**，做法见下面第 1 步。
3. **Python 3.10 或更高版本**：trio 的几个小脚本要用。
4. **一个放应用的项目文件夹**：还没有的话，让审查者帮你建成一个 git 仓库，你不需要学 git。
5. **一些不真实的样例数据**，或者允许 agent 自己编。agent 只在编出来的数据（合成数据）上测试。

## 七个步骤

### 1. 安装 trio

trio 是一个插件，里面装着一个技能，也就是 agent 要遵循的那套说明。两个工具里都要装。

**Claude Code**：在终端里运行这两条命令。

```bash
claude plugin marketplace add yuson95/trio-workflow
```

```bash
claude plugin install trio-workflow@trio
```

**一条命令装进好几个工具**（Claude Code、Codex、Cursor；需要 Node.js 22.20 或更高版本）：用的是 Vercel 开源的 `skills` 安装工具。

```bash
npx skills add yuson95/trio-workflow -g -a claude-code -a codex -y --copy
```

要装进 Cursor，就再加 `-a cursor`。以后运行 `npx skills update -g`，就能更新到最新的 trio。这个安装工具默认会发送匿名使用统计，设置 `DISABLE_TELEMETRY=1` 可以关掉。

**没有 Node.js**：先下载仓库，再把 trio 复制进每个工具。

```bash
git clone https://github.com/yuson95/trio-workflow.git
```

```bash
python trio-workflow/tools/install_local.py install --target codex
```

按你用的工具选目标：`claude`、`codex`、`cursor`。

**每个工具只用一种装法**：用了两种，工具里会出现两份 trio。

**其他 agent**：把 `plugins/trio-workflow/skills/trio-workflow/SKILL.md` 的完整路径写进它的指令里，具体见插件的 README。

### 2. 让审查者搭好项目

在你的项目文件夹里打开审查者，说：

> 为这个项目搭建 trio 工作流。审查者用 <工具 A>，执行者用 <工具 B>。

它会在一条消息里问齐所有问题，每个都带默认值：

- 目标是什么；
- 客户数据放在哪；
- 哪些内容可以发到外部；
- 你用哪句话允许合并。

知道的就回答，其余用默认值。然后它会在项目旁边建一个**交接目录**。所有 agent 都在这里读写文件，所以不依赖任何一个对话。

### 3. 说清你想要什么

告诉审查者：

- 这个应用做什么用；
- 谁会用；
- 怎样才算好。

你喜欢的工具的截图、你现在在用的表格、纸上画的草图，都比长篇文字更管用。

审查者会读现有代码，把不确定的地方先试一遍，然后写出**方案一**：

- 每条需求写明你会在屏幕上看到什么；
- 每处界面改动都附**原型**，也就是写代码之前先画出页面的样子；
- 每个待定的问题都带默认值。

你确认原型，或者从几个变体里选一个。

### 4. 启动执行者

打开执行者，把审查者写在交接目录 `PROMPTS` 文件里的开工提示词贴进去。执行者会自己一直做到第一个**停点**，也就是事先定好、停下来接受审查的时间点。到了停点，它只回一句话，比如“已到停点 1，材料在 …”。

### 5. 每个停点都做独立审查

**新开**一个审查者对话，说“审查方案一停点1”，并附上执行者那句话。审查者会自己重跑检查，在用合成数据的副本上实际操作页面，然后写一份结果文件。文件最后有三样东西：

- **结论**：PASS（通过）、PASS+NOTES（通过但有备注）或 FAIL（不通过）；
- 需要你做的少数几个**决定**，每个都带默认值；
- 一段转给执行者的话。

回答决定，或者不回答、全部按默认。然后告诉执行者：“审查结果见 <路径>，请按结果修改后继续。”

注意：结果文件写明通过之前，不要告诉执行者“通过了”。

### 6. 走查真实页面

在方案结束之前（改动页面多的方案，中途还会加一次），执行者会准备一个已经算好结果的测试副本，给你三样东西：

- 一个可以打开的地址；
- 一份按顺序要看的页面清单；
- 一张截图对照表：每个页面一行，每种情形一列（空项目、完整、记录很多、窄屏），新旧版本并排。

用大白话说出哪里不对劲。审查者会把每条意见分到四类里的一类，并确保每条都有长期的解决办法：

| 类别 | 长期解决办法 |
| --- | --- |
| 违反约定 | 写进规则，再加一项自动检查 |
| 规格没写到 | 在模板里加一项 |
| bug | 补一个测试 |
| 品味 | 给你几个原型选 |

### 7. 完成方案

最终审查写明 PASS 之后，对审查者说“合并并推送”（或“只合并不推送”）。它会合并、核对结果，如果你的应用在运行，还会把它重启。然后方案二从第 3 步开始。

## 你会遇到的词

| 词 | 意思 |
| --- | --- |
| **方案** | 一块有目标、有需求、有停点的工作，通常几天到两周 |
| **停点** | 事先定好的时间点，执行者停下，审查者独立检查 |
| **批次** | 方案里的一小块，由一个执行子 agent 完成并自证 |
| **结论** | 审查者给的 PASS、PASS+NOTES 或 FAIL，绑定到代码的某个确切版本 |
| **原型** | 页面做出来之前先画出的样子 |
| **走查** | 你在测试副本上实际操作页面 |
| **合成数据** | 编出来、看起来像真的数据；agent 只用它测试 |
| **main** | 应用的正式版本；只有你说“合并”之后，改动才会进入它 |
| **交接目录** | 存放方案、进度文件和审查结果的文件夹 |
| **PR 模式** | 可选：每个批次都开一个带自动测试的 PR，停点照旧。项目放到 GitHub 上之后再考虑 |

## 常见错误

| 错误 | 正确做法 |
| --- | --- |
| 审查还没完成，就告诉执行者通过了 | 等结果文件。它常常能发现执行者自查时漏掉的问题 |
| 检查全部通过，就跳过走查 | 检查通过不代表页面合理，这只有你能判断 |
| 执行中途直接给执行者提新要求，没告诉审查者 | 告诉审查者，由它记下来、决定放进哪个方案 |
| 一个特别大的方案 | 拆成几个方案，每个一到两周，每个结束时都能用上 |
| 让 agent 处理真实的客户文件 | 真实数据放在项目外面，agent 只用合成副本 |
